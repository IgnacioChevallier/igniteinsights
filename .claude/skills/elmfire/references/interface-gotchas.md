# ELMFIRE interface gotchas

Concrete ways to accidentally break ELMFIRE's inputs/outputs. Sourced from the
vendor ELMFIRE 2025.0212 tutorials and cross-checked against this repo's code where
noted.

## Raster filenames are a fixed vocabulary, extensionless in the namelist

ELMFIRE expects exactly these basenames (files on disk are `.tif`, but the namelist
value has no extension — ELMFIRE appends it):

```
dem, slp, asp, fbfm40, cc, ch, cbh, cbd, ws, wd, m1, m10, m100, adj, phi
```

Confirmed in both `app/elmfire/builder/namelist_writer.py` and the vendor tutorials'
`FLOAT_RASTER[n]=<name>` / `INT_RASTER[n]=<name>` convention. Do not add a `.tif`
suffix to these values in the namelist.

## Int16 canopy rasters use LANDFIRE-style unit scaling

`ch` (canopy height), `cbh` (canopy base height), and `cbd` (canopy bulk density) are
written as Int16 to preserve precision without floats, using LANDFIRE's scaling
convention:

- `ch`, `cbh`: value = **10 × meters** (e.g. 1.5 m → `15`)
- `cbd`: value = **100 × kg/m³** (e.g. 0.12 kg/m³ → `12`)
- `cc` (canopy cover) is a plain percent 0–100, no scaling.

**This repo already implements this correctly** — `app/elmfire/builder/canopy_builder.py`
pre-scales `cbh`/`cbd` inside `derive_cbh_cbd` (derived from `cc`/`ch`) and applies
`scale_factor=10.0`
for `ch` reprojection. If you're touching canopy code, verify any new derivation still
respects this scaling — feeding raw meters/kg-m³ into an Int16 raster ELMFIRE expects
to be pre-scaled will silently corrupt fire behavior calculations (values will look
plausible, just off by 10x/100x).

## Weather/moisture time series never reach ELMFIRE as CSV

Vendor tutorials show weather defined in a `wx.csv` (columns `ws,wd,m1,m10,m100,lh,lw`,
one row per time band, no explicit time column) — but **ELMFIRE never reads `wx.csv`
directly**. The tutorial's `01-run.sh` script parses it and burns it into multiband
GeoTIFFs (`ws.tif`, `wd.tif`, etc.), which is what the namelist actually points to.
The uniform time spacing between bands is set via `DT_METEOROLOGY` in `&INPUTS`
(seconds); ELMFIRE linearly interpolates between bands at its internal timestep. This
repo's `weather_builder.py` follows the same pattern (writes multiband rasters
directly, no CSV intermediate), and `write_namelist(dt_meteorology_s=3600.0)` writes the
spacing — if it changes (e.g. sub-hourly weather), the raster band count has to change with
it; `validate_weather_coverage()` rejects rasters with too few bands for `TSTOP`.

## Coordinate systems: two different conventions in the vendor docs, don't conflate them

- Idealized tutorials (01/02) use a domain **centered on the origin**: lower-left
  corner at `(-DOMAINSIZE/2, -DOMAINSIZE/2)`.
- Real-world tutorials (03/04) and this repo use the **raster's own bounds**: ELMFIRE
  reads `COMPUTATIONAL_DOMAIN_XLLCORNER`/`YLLCORNER` directly from the DEM's actual
  extent (see `namelist_writer._read_domain()`), no origin-centering involved. Ignition
  coordinates in real-world tutorials are in the DEM's **projected CRS (UTM meters)**,
  never lat/lon.

Don't assume the idealized tutorials' origin-centered convention applies to this repo.

## Output file naming (relevant to `app/postprocessing/`)

With `DUMP_TIME_OF_ARRIVAL`/`DUMP_FLIN`/`DUMP_SPREAD_RATE` (this repo's current
settings) and `CONVERT_TO_GEOTIFF = T`, ELMFIRE itself writes per-ensemble-member,
per-dump-time GeoTIFFs — real names are `time_of_arrival_*.tif`, `flin_*.tif`,
`vs_*.tif` (spread rate — **not** `spread_rate_*.tif`, and **not** `toa_*.tif` for
time of arrival). `XXXXXXX`/`YYYYYYY` suffixes are ensemble-member ID and dump time
in seconds respectively.

**`hourly_isochrones.shp` is not a native ELMFIRE output.** There is no
`SAVE_ISOCHRONES`/`DUMP_ISOCHRONE_SHAPEFILES`-style flag anywhere in ELMFIRE's
source (`github.com/lautenberger/elmfire`). It's generated by **external
post-processing** in the elmfire-runner microservice
(`elmfire-runner/app/runner.py`), which runs `gdal_contour -i <DTDUMP>
time_of_arrival_*.tif hourly_isochrones.shp` after ELMFIRE exits successfully. Don't
go looking for an isochrone-related namelist keyword — it doesn't exist; if isochrone
output is ever wrong, the bug is in the runner's `gdal_contour` invocation, not in
`elmfire.data`. This repo's `app/postprocessing/isochrone_converter.py` consumes the
resulting `hourly_isochrones.shp` — don't change `DTDUMP` or output filenames without
checking that consumer and the runner's `gdal_contour` call stay in sync.

## `MODE=2` (fire-potential) is a structurally different namelist, not just extra keywords

Not used by this repo today, but if it's added later: `MODE=2` in `&SIMULATOR` drops
`&TIME_CONTROL` entirely (timestep/CFL/stop-time don't apply) and replaces point
ignition (`X_IGN`/`Y_IGN`/`T_IGN`) with a `&MONTE_CARLO` band sweep
(`METEOROLOGY_BAND_START`/`STOP`/`SKIP_INTERVAL`). Treat this as a separate namelist
template, not a couple of extra keywords bolted onto `write_namelist()`.

## `DTDUMP` must be strictly less than `TSTOP`, or ELMFIRE never dumps output

If the output dump interval (`DTDUMP`) is `>=` the simulation stop time
(`SIMULATION_TSTOP`), ELMFIRE's only possible dump checkpoint coincides with the
run's final instant — which can mean the run "succeeds" but writes no raster/isochrone
output. `namelist_writer.resolve_dtdump_s()` clamps `dtdump_s` to `tstop_s / 2` when
this would happen. `app/api/v1/simulations.py` reads back the *resolved* `dtdump_s`
from `write_namelist()` and forwards it to the runner request (`dtdump_s` field on
`SimulationRequest`) — don't hardcode `dtdump_s` in the runner call path, always use
the value `write_namelist()` actually resolved to, or the two will disagree again.

## `PHI_FILENAME` values more negative than -1.1 get silently reset to "unburned"

ELMFIRE's raster loader (`elmfire_io.f90`, reading `PHI0` from `PHI_FILENAME`) does
`WHERE(PHI0 < -1.1) PHI0 = 1.0` right after reading the raster — any value more
negative than -1.1 is treated as garbage/nodata and reset to +1.0 (unburned), no
warning printed. `app/elmfire/builder/ignition_builder.py` writes `phi.tif` as a
signed-distance-in-meters field (buffer radius × cell size, e.g. -90 for a 90 m
buffer) — unclamped, every interior "on fire" cell is erased before the simulation
starts and the run reports `Fire area: 0.0` whatever the weather and fuel.

Fix: clamp the *negative* (interior/ignited) side of the signed-distance field to a
floor just above -1.1 (`PHI_IGNITION_FLOOR = -1.0` in `ignition_builder.py`, also used by
`app/playground/builder.py`) before writing —
`np.where(phi_m < 0, np.maximum(phi_m, PHI_IGNITION_FLOOR), phi_m)`. Leave positive
(unburned/outside) values as true physical distances; only the interior needs
clamping. The vendor tutorials sidestep this entirely by initializing `phi.tif`
uniformly to `+1.0` and igniting via `&SIMULATOR` point ignitions
(`NUM_IGNITIONS`/`X_IGN`/`Y_IGN`/`T_IGN`) instead of a spatial phi raster — this repo
uses the raster approach instead, so the clamp is required.

## Crown fire is on by default upstream

If a namelist omits `CROWN_FIRE_MODEL` entirely, ELMFIRE defaults to crown fire
**enabled**. `namelist_writer.py` therefore always writes it (`DEFAULT_CROWN_FIRE_MODEL = 1`,
overridable through `write_namelist(crown_fire_model=...)`) — don't drop the keyword
from the template, or the setting silently becomes ELMFIRE's default again.

## `asp` is the direction the slope FACES (downslope), not the upslope bearing

ELMFIRE 2025.0212 pushes slope-driven spread toward `ASP − 180°`
(`elmfire_level_set.f90`: `SINASPM180(IASP) = SIN((IASP − 180) · π/180)`), which is upslope only
if `ASP` is the LANDFIRE aspect: the azimuth the slope faces, i.e. downslope. Until
`raster_aligner.DERIVATION_VERSION = 3` (2026-09-28) this repo wrote the **upslope** bearing, and
every run pushed fires **downhill** (found in RESULTADOS-CSS-BAP, loop 2: 150 m along `asp`, the
terrain rose in 96 % of cells steeper than 20°). `tests/test_topo_aspect.py` pins the convention
with synthetic slopes: a slope rising to the north faces south (180).
